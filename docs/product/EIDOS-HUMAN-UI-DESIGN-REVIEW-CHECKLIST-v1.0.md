# Eidos Human UI Design Review — 必经检查 v1.0

**Authority:** 此规范从 `EIDOS-HUMAN-EXPERIENCE-DESIGN-AUTHORITY-v1.0.md` 派生，适用 Eidos、Workbench、Host、plugin Experience、移动与桌面、LLM 生成或修改的任何 Human 界面；**不是独立于 Eidos 的第二套设计语言**。2026-10-15 纳入流程、视觉、注意力、工作记忆及跨年龄研究。

## 1. 对所有界面设计 LLM 强制的工作顺序

**MUST：在生成/修改页面、导航、控件布局、交互流程、提示文案、配色或操作按钮前：**
1. 阅读本规范及 `EIDOS-HUMAN-EXPERIENCE-DESIGN-AUTHORITY-v1.0.md`，完整读取涉及任务的权威导航/交互/视觉/移动/可访问性章节。按项目读取规范记录读过的范围；不能只读标题或外部搜索摘要。
2. 明确 Human 真正的目标、任务上下文、角色/权限、输入与完成条件；判断直接操作、引导流程和 Agent 协作的最低总成本方案。
3. 从 `Experience Architecture Constitution` 定义起点→有效动作→结果→失败→断点恢复；**衡量需要记忆的事项**，不能以页面数量少掩盖 20+ 个选择的认知成本。
4. 按 Navigation & IA 决定入口是否必要、属于哪一层、是否有重复导航及是否应保持同一任务页面；不要暴露内部运行路径与 UUID。
5. 按 Productive Design Language 和 Business Office Visual Language 规定主按钮唯一性、先结果后例外、分组/留白/密度、已有 token/字体/语义色、易读的表格与渐进展开。沿用 Eidos 正式 tokens，不可从外部设计规范硬拷 CSS。
6. **检查记忆与注意力**：让用户识别当前/历史选择而不是重新回忆；系统保存草稿、上次选择、来源上下文、当前进展、问题原因；切页/中断可恢复、不需重复输入；无年龄刻板化，仅提供可读且可缩放默认界面及可选高级明细。
7. 按可访问性/移动规范查对比度、状态不只靠颜色、焦点/键盘、44px 触控目标、中文排版/放大/窄屏、一致返回与错误解释。
8. 对副作用和数据所有权复核：LLM 自动推荐不得取代 Human 授权；业务写入、权限、审计与安全校验仍完整；允许错误后合法纠错与重试，保留数据原值。
9. 对现有组件与过去研究做最小复用：先查 Eidos 的原有规范、复用现有能力，缺少模式才提交新的通用能力。外部研究只能支持选择，不能推翻 Eidos 权威。
10. 在实现 PR 中留下**可审核的 UI 设计检查记录**（下方模板）；同时以真实业务路径/浏览器或等效测试验证。没有真实运行证据不得标记实测已通过。

**优先级：** 可访问性/安全与业务权威 > Experience Architecture > Navigation/IA > 交互规范 > Eidos Business Office 视觉规范 > 响应式实现 > 外部研究/视觉潮流。

## 2. 每个 UI PR 的检查记录（内容可直接复制）

> 应随 UI 修改 PR 一起提交到调用仓库 `docs/ui-design-reviews/<scope>-<YYYYMMDD>.md`。不能只留在聊天中；若确实无 UI 变更，无需填写。

| 必需检查域 | 需在 PR 文档给出的简短、可验证信息 |
|---|---|
| `## 目标与完成条件` | 谁、为什么来、什么叫完成；业务对象/状态及权限 |
| `## 流程与步骤` | 原/新步骤；能否合并，为什么不省略校验；直操作 vs Agent |
| `## 导航与信息架构` | 入口/上下文/是否重复菜单；为何同屏或跳转 |
| `## 视觉与颜色` | 对应 Eidos tokens/设计语言；对齐/标题/密度/主次操作、状态色 |
| `## 记忆与注意力` | 如何保留历史、避免强迫回忆、中断继续、例外优先与纠错 |
| `## 无障碍与跨年龄` | 对比度、焦点、可缩放文字、触屏、中文/窄屏，非年龄刻板模式 |
| `## 安全与数据修复` | 权限/创建/提交边界，来源留存，错误更正/撤销策略 |
| `## 证据与剩余问题` | 源文档、截图/测试、CI 与真实验收；未做的如实记载 |

**每个必需域要有具体内容，不是打勾代替设计。** 不能用「待验证」冒充通过，不能让 LLM 生成通用套话而缺少业务路径。明确分开「规范符合」「自动化通过」「真实 Human 验收」。

## 3. 认知负荷检查的判定示例

- 有 22 个来源列：不是默认呈现 22 组大号字段控件，而是先恢复历史映射→只列异常→按需查看全部来源→一次批量审核。
- 有两个同名业务字段：显示来源/候选说明让人选对，不自行合并同名目标。
- 在某一步需要记住前一页选择：判定为未通过，除非两处相关信息在当前屏就地可见或者可即时召回。
- 有长时间 AI 分析：显示当前进展、来源和可继续任务，不让人重新操作；AI 失败仍可人工处理。
- 已提交的数据不能随意覆盖：允许业务 owner 支持的修订/重导入，保留审计而不是静默改旧值。
- 按年龄判断“40+ 记忆差”：判定不合格。可读性、字号、操作大小、清晰反馈对所有人默认适用。
- Cowan “4 组块”是受条件限制的研究结论，不等于 UI 限制 4 个按钮；减少工作记忆依赖通过可见信息与恢复机制来落实。

## 5. 机械门禁与人类验收界限

此文档是 **LLM/开发工作规范**；对连接 GitHub 的 PR 需要配套 CI：
- 变化涉及 Human 页面/导航/标准布局时，CI 要求同 PR 存在新增或更新的 `docs/ui-design-reviews/*.md`，且包含全部必需域；
- CI 可以验证记录存在、章节完整、关联 PR 的变更文件，但**不能证明视觉设计真的好用**。人工/实际操作验收仍不可跳过；
- 独立应用仓库也应执行同等规则（EVO-App-Platform 配套自己的 PR gate）；
- 本规范无法控制未连接仓库、不经过 PR 的任意 LLM；不要把“代码检查”宣称为对世界所有 LLM 的强制拦截。
