# Eidos Promotion & Adoption Plan

## 1. Positioning

Do not lead with "another UI framework".

Lead with:

> **Eidos is the deterministic Experience system for LLM-built software. It reduces the amount of UI code an LLM must invent and moves correctness into explicit capabilities, contracts and validators.**

Secondary line:

> **LLM proposes. Eidos validates. Humans decide. Host executes.**

## 2. The three proofs

Every public explanation should prove, not merely claim:

### Proof A — Less invention
Show the same task as framework-code generation vs Eidos capability composition. Measure generated code/tokens and repair cycles.

### Proof B — Fail closed
Inject an invalid capability or integrity violation. Show deterministic rejection and a machine-actionable diagnostic.

### Proof C — Human usefulness
Show a polished decision/exception experience and direct drag/reorder. Eidos is not only safe for machines; it must be efficient for people.

## 3. Audience sequence

### First: LLM / agent builders
They feel the generated-code reliability problem most directly.
Offer: tool protocol, capability catalog, evaluation suite, sample agent adapter.

### Second: AI application engineering teams
Offer: Forms/Data + Decision + BI capability packs, Host boundary patterns and deployment starter.

### Third: enterprise platform teams
Offer: private capability registry, policy packs, audit/observability, compatibility governance, collaboration and accessibility controls.

### Fourth: product/operations buyers
Sell outcomes: faster task-specific experiences, better exception handling, focused human decisions.

## 5. Launch narrative

### Phase 1 — Technical credibility
Publish:
- Constitution;
- deterministic contracts;
- LLM evaluation;
- benchmark methodology;
- demo source;
- failure cases, not only successes.

Goal: earn trust from engineers and model/agent developers.

### Phase 2 — Visual credibility
Publish polished examples:
- executive exception review;
- finance decision review;
- collaborative incident review;
- BI analysis;
- process/diagram editor;
- spatial/digital-twin review.

Goal: remove the impression that Eidos is only an architecture experiment.

### Phase 3 — Integration credibility
Demonstrate at least:
- one real LLM/agent;
- one EC-style producer;
- one real Host API;
- one enterprise auth/policy integration;
- one deployment on static/cloud infrastructure.

### Phase 4 — Ecosystem
Invite external capability/renderer contributions through an admission test:
- semantic contract;
- deterministic schema;
- accessibility;
- state ownership;
- renderer independence;
- LLM discoverability;
- tests;
- docs.

## 7. Benchmark program

Create repeatable tasks:
1. CRUD/form task;
2. exception review;
3. finance analysis;
4. collaboration task;
5. process diagram;
6. spatial review.

For each compare:
- raw framework generation;
- framework + component library;
- Eidos composition.

Measure:
- generated tokens/code;
- first-pass success;
- repair cycles;
- accessibility defects;
- state/event defects;
- time to usable experience.

Do not publish superiority claims before the benchmark data supports them.

## 8. Feedback loop

External feedback enters stable taxonomy codes in `feedback/ISSUE-TAXONOMY.md`.

Prioritize fixes in this order:
1. reliability / validator gaps;
2. contradictory context;
3. LLM capability hallucination;
4. Host/business boundary violations;
5. human decision integrity;
6. direct-manipulation friction;
7. missing high-frequency capability;
8. visual polish;
9. long-tail capability breadth.

## 9. What not to do

- Do not market planned capabilities as production complete.
- Do not imply Eidos is an LLM model.
- Do not hide failure cases.
- Do not compare only screenshots.
- Do not require users to understand EVO or Experience Compiler internals.
- Do not let public examples bypass the Host boundary.
- Do not optimize component count at the expense of LLM error surface.

## 10. Success criteria

Technical:
- independent LLMs converge on the same core mental model;
- low first-pass invalid proposal rate;
- deterministic validator catches contract/invariant violations;
- common experiences require materially less generated implementation code.

Product:
- a new human understands the value within one demo;
- direct customization is faster than conversational modification for simple tasks;
- decision/exception examples feel production-oriented.

Market:
- external teams can build a POC without project-author intervention;
- third parties can add a capability from the admission guide;
- real integration requests become more specific than "what is this?".
